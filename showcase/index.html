ReturnGuard reviews online-shop return and refund requests with ten specialised AI agents. They check the order, the store policy, the photo and the customer’s history — but nothing is refused without a person, large refunds always go to a human, and every decision can be traced to the exact model, prompt and policy that produced it.

The problem

Every return needs a judgement call.

“It arrived broken.” “Wrong item.” “Changed my mind.” Each request means checking the order, the return policy, the photo and the customer’s history. Some are fraud: AI-generated damage photos, serial returners, rings of accounts sharing an address or card.

Doing it all by hand is slow and expensive. Handing it all to a model is reckless — a model that can silently issue refunds can be talked into issuing refunds. ReturnGuard is the middle path: agents do the legwork, and the system only acts inside limits a human set.

How a return is reviewed

Ten steps, each one logged.

Every step records which model ran, a hash of its input, its output, confidence, tokens, cost and latency — and streams live to the reviewer’s screen.

  1. Data-quality gateNot enough evidence? Straight to a human — never guess.fast LLM
  2. PlannerDecides which checks this case actually needs.fast LLM
  3. IntakeDoes the story match the reason and the amount?fast LLM + order tool
  4. PolicyRetrieves the current versioned policy text and judges eligibility. Dates and thresholds are computed in code.reasoning LLM + RAG
  5. ImagePhoto vs. catalogue image, plus an AI-generated-photo detector. Signals only.local CLIP + detector
  6. BehaviourAccount risk score and shared-fingerprint fraud-ring check.local ML model + LLM
  7. DecisionCombines every signal: approve, deny or escalate.reasoning LLM
  8. CriticSecond opinion. Can veto to a human — never to a different automatic outcome.careful LLM
  9. ExplanationPlain-language reason for the customer and the audit trail.careful LLM
  10. Governance gateThe only step that can finalise anything. Rules live in Open Policy Agent, not in prompts.policy-as-code

Guardrails

Rules no prompt can switch off.

No automatic refusals

A proposed denial always becomes an escalation. Only a person’s explicit confirmation can deny — even at 96% model confidence.

Bounded auto-approval

Risk below 0.30, confidence at least 0.80, no Critic veto, and under $250 — all at once, or a human decides.

Kill switch

One admin control sends every case to a person, checked fresh on every case — no restart.

Least privilege per agent

Each agent has its own identity, tool grant, model grant and budget. The image agent can call zero tools — proven by trying.

Appeals to someone else

A declined customer can appeal; it routes to a different reviewer, and the original one gets a hard rejection if they try.

Tamper-evident record

Every human and agent action lands in a hash-chained audit log that can be re-verified at any time.

Autonomy is earned, one level at a time

  1. ShadowAI runs and is logged; people decide everything. Default.
  2. SuggestReviewer’s screen opens pre-filled with the AI’s proposal.
  3. AssistAuto-approves low-risk cases; 10% still sampled for a human check.
  4. AutoAuto-approves low-risk cases without sampling.

Architecture

Everything a real deployment needs.

  • Agents LangGraph pipeline with a Postgres checkpointer
  • LLM gateway Bifrost: Groq first, OpenAI fallback, per-agent keys and budgets
  • Tool governance IBM ContextForge (MCP), one virtual server per agent
  • Policy Open Policy Agent, with unit tests, failing closed
  • Identity Keycloak for people and one service account per agent
  • Data Postgres, Qdrant (policy RAG), MinIO, Redis, Vault
  • Local ML CLIP, an AI-image detector, a calibrated gradient-boosted risk model
  • Observability Langfuse traces, Prometheus, Grafana, alert rules
  • App FastAPI backend, Next.js shop and reviewer console
